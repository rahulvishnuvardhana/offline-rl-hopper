## 1. Requirements

### 1.1 Research question
As the fraction `p` of expert data in an offline dataset grows, how quickly do BC and IQL reach expert performance, and does IQL's expectile `tau` matter more when expert data is scarce?

### 1.2 Hypotheses (pre-registered; do not change after seeing results)
- **H1:** BC's score rises with `p`, possibly non-monotonically (a unimodal Gaussian policy may average expert and simple behavior).
- **H2:** IQL reaches near-expert performance (normalized score >= 90) at a much lower `p` than BC.
- **H3:** Higher `tau` helps IQL more at `p = 0.05` than at `p = 0.5`.

### 1.3 Functional requirements
| ID | Requirement |
|---|---|
| F1 | Download and validate `mujoco/hopper/expert-v0` and `mujoco/hopper/simple-v0` from Minari. |
| F2 | Build mixtures of exactly 900,000 transitions with expert fraction `p` in {0, 0.05, 0.2, 0.5, 1.0}, sampled by whole episodes, deterministic given a seed. |
| F3 | Train BC and IQL from a single YAML config per run. BC is IQL's policy loss with `beta = 0`, same network. |
| F4 | Evaluate in the recovered Hopper-v5 env: 10 episodes every 5,000 gradient steps, deterministic (mean) action. |
| F5 | Log per-step losses and per-eval returns to disk (CSV + TensorBoard), checkpoint so a killed job can resume. |
| F6 | Launch the whole grid on Explorer with one command (Slurm job array). |
| F7 | Produce the main figure, learning curves, ablation plot and results table from logs with one command. |

### 1.4 Non-functional requirements
| ID | Requirement |
|---|---|
| N1 | **Reproducible:** same config + seed gives the same mixture and (on CPU) the same first 100 losses. Every run saves its resolved config, git commit hash and package versions. |
| N2 | **Tested:** unit tests on the losses, the mixture builder and the data pipeline; CI runs them on every push. |
| N3 | **Portfolio-grade:** clean package layout, README with results figure, `ruff` lint clean, type hints on public functions, MIT license. |
| N4 | **Fair comparison:** BC and IQL share network, data, optimizer, batch size, step budget and eval protocol. |
| N5 | **Honest statistics:** report mean, std and bootstrap confidence intervals; never pick seeds. |

### 1.5 Out of scope
Online fine-tuning, image observations, environments other than Hopper, hyperparameter tuning per `p` (we use one published setting everywhere; tuning per cell would bias the comparison).

## 2. Is the data available, and is it clean?

**Available: yes.** Both datasets are public on Minari (Farama Foundation), hosted on Hugging Face. No collection is needed. [5]

| | `expert-v0` | `simple-v0` |
|---|---|---|
| Steps | 999,164 | 999,206 |
| Episodes | 1,086 (about 920 steps each) | 1,952 (about 512 steps each) |
| Generated by | SB3 SAC trained 25M steps [11, 12] | SB3 SAC trained 1M steps |
| Env | Hopper-v5, max 1,000 steps | same |
| Obs / action | `Box(11,)` float64 / `Box(3,)` in [-1, 1] float32 | same |
| File size | 135 MB | 148 MB |
| Pinned deps in metadata | mujoco==3.2.3, gymnasium>=1.0.0 | same |

**Clean: probably, but "clean" is something we verify, not assume.** Minari datasets are curated and no NaN or corruption reports exist for these two. But there are real traps that will silently break offline RL if handled wrong:

1. **Observations have N+1 entries** per episode (initial + final). `next_obs = obs[1:]`, `obs = obs[:-1]`. Off-by-one here corrupts every TD target.
2. **Terminations vs. truncations.** Bootstrap mask is `1 - terminations` only. A truncation at step 1,000 is NOT a terminal state. Treating it as terminal teaches the agent that surviving to step 1,000 is worth zero future value.
3. **No reference scores.** `get_normalized_score()` fails on these datasets (Minari issue #323). D4RL's hopper constants come from older Hopper versions with a different reward, so they are not valid here. We define our own normalization (Section 6, Phase 4).
4. **float64 observations.** Cast to float32 once, at load time.
5. **Scale differences across state dimensions** (positions vs. velocities). Requires state normalization (Phase 3).

Phase 2 turns "probably clean" into "verified clean" with a written EDA report.

| # | Decision | Reason | Alternative rejected |
|---|---|---|---|
| ADR-1 | Self-written BC and IQL in PyTorch; CQL (optional) uses CORL unchanged with a Minari loader | Learning goal + full control of the "one design choice differs" comparison | Using CORL for everything (less learning, harder to guarantee identical BC/IQL setup) |
| ADR-2 | BC = IQL policy loss with `beta = 0`, same Gaussian policy | Any gap is attributable to value learning only [1] | CORL's deterministic MSE BC (different network and loss, confounds the comparison) |
| ADR-3 | Follow the **IQL paper's** MuJoCo settings, not CORL's per-dataset configs. ~~Two deviations, both as in CORL: the reward-scale min/max uses complete episodes only, and states are normalized (the original IQL code does neither)~~ (corrected 2026-11-21, at Phase 5 close) Two deviations from the original IQL code, which does neither: the reward-scale min/max uses complete episodes only, and states are normalized as in CORL. CORL's reward-scale range also closes an episode at its 1000-step counter; ours uses complete episodes only (ADR-9; Phase 5 spec Section 3) | One published setting for all `p`; CORL's hopper configs differ between datasets | Tuning per `p` (biases the comparison) |
| ADR-4 | Mixture defined by **transitions**, sampled by whole episodes, trimmed to exactly 900k | Simple episodes are about half as long as expert ones | Mixing by episode count (would make `p` misleading) |
| ADR-5 | Normalizers are fit on **each mixture**, never on the full expert data | Fitting on expert data leaks information into low-`p` runs | Global normalizer |
| ADR-6 | Own score normalization, D4RL convention: 0 = random-policy mean return, 100 = expert dataset mean return; raw return and fall rate always reported too. Revised 2026-11-15, before any training result, because the returns are bimodal (spec `docs/specs/phase-2b-eda.md` Section 5) | Minari has no reference scores for these datasets; a simple-mean zero point sits in the gap between falling and non-falling episodes | D4RL constants (wrong env version); 0 = simple dataset mean (the original proposal) |
| ADR-7 | Plain YAML configs + a tiny loader, CSV + TensorBoard logging | Few dependencies, works offline on the cluster, free | Hydra (learning cost), W&B (optional, see Open Questions) |
| ADR-8 | Data, envs and checkpoints on `/scratch`; code and final results in git | Home quota is 75 GB and fixed; scratch is purged monthly, so anything precious is copied out | Everything in `/home` |
| ADR-9 | IQL reward scale `1000 / (max_ret - min_ret)` per mixture, over its untrimmed episodes (decided 2026-11-15, `docs/specs/phase-3-mixtures.md` Section 4) | Faithful to the paper's rule; for every `p >= 0.01` the scale is 0.25 to 0.27, so H2 and H3 are unaffected. Caveat, stated in the report: at `p = 0` the scale is 1.4x larger, so IQL's effective `beta` there is about 4.4 instead of 3; every run logs `beta_eff` | One fixed scale for all `p` (departs from the paper; a data-derived constant carries expert information into `p = 0`) |

## 4. Compute plan: Explorer HPC and Slurm

### 4.1 How much GPU do we actually need?
Honest answer: **very little.** Our networks are 256x256 MLPs with batch 256. A modern GPU is mostly idle on one run, and evaluation rollouts in MuJoCo run on the CPU. So:

- **One GPU per job, any type.** V100 or T4 is plenty. Do not request A100 or H200: they are overkill and queue longer.
- **Pack several runs per GPU** (run 2 to 4 training processes in parallel inside one job) to use the GPU properly.
- **Measure before scheduling** (Phase 6). Rough guess to be replaced by the benchmark: 20 to 60 minutes per 300k-step run including eval. 42 core runs is roughly 15 to 40 GPU-hours, which fits easily.
- CPU-only on the `short` partition is a valid fallback and has a much higher running-job limit. Phase 6 benchmarks both and picks the faster wall-clock.

### 4.2.1 Responsible-use rules (the condition of the approval)
1. **Smallest request that works:** 1 GPU of any type, `--time` = measured runtime + 50%, `--mem` and `--cpus-per-task` from the Phase 6 benchmark, not guesses.
2. **No idle GPUs:** never hold an interactive GPU session while reading or writing code; use `gpu-short` for tests and exit when done. Debug on your laptop CPU first.
3. **No speculative grids:** the grid is submitted only after Phases 4 to 6 DoDs pass, and only once per code version. Failed bundles are resubmitted, not the whole array.
4. **Throttle arrays** (`%4`) so you never exceed the partition's running-job limit or crowd out the LLM course's students. Avoid launching big arrays right before that course's deadlines.
5. **Cancel bad runs early:** check the first bundle's log within 15 minutes; `scancel` anything diverging or misconfigured.
6. **Clean storage:** delete checkpoints except the final one after Phase 9; keep scratch under a few GB.
7. **Keep a usage log** (`report/compute.md`): total GPU-hours used, so you can show the professor what was consumed if asked.

### 4.3 Job layout
- `slurm/grid.sbatch` is a **job array**: one array task = one bundle of 2 runs that share a GPU.
- Main grid: 30 runs / 2 per task = 15 array tasks, throttled with `%4` to match the 4-running-job limit on `gpu`.
- Every run checkpoints every 25k steps and resumes automatically, so the 8 h limit and pre-emption cannot lose more than 25k steps.

```bash

#SBATCH --partition=gpu
#SBATCH --gres=gpu:1                 # any type; pin with gpu:v100-sxm2:1 if needed
#SBATCH --cpus-per-task=8            # eval rollouts are CPU work
#SBATCH --mem=32G
#SBATCH --time=04:00:00
#SBATCH --array=0-14%4
#SBATCH --output=logs/%x_%A_%a.out
```

## 5. Techniques that matter for good, trustworthy results

These are the implementation details that separate "IQL works" from "IQL mysteriously scores 30". All are from the IQL paper, its official code, or CORL [1, 8]. Implement them all; list them in the report.

| Technique | Setting | Why |
|---|---|---|
| State normalization | `(s - mean) / (std + 1e-3)`, fit on the mixture, same transform at eval | Velocity dims dwarf position dims; standard in TD3+BC and CORL [8, 16] |
| Reward scaling (IQL only) | `r * 1000 / (max_episode_return - min_episode_return)` computed on the mixture | IQL paper's locomotion setting [1] |
| Twin Q, take the min | Two Q heads; V target uses `min(Q1, Q2)` from the target network | Reduces overestimation |
| Target network | Soft update rate 0.005 | IQL paper Appendix B [1] |
| Advantage weight clip | `exp(beta * (Q - V))` clipped at 100 | Prevents a few huge weights dominating the policy loss |
| Actor LR schedule | Cosine decay on the actor only | IQL paper [1] |
| Log-std clamp | `log_std` in [-20, 2], state-independent | CORL GaussianPolicy |
| Hyperparameters | `tau = 0.7`, `beta = 3`, lr 3e-4 (all nets), batch 256, gamma 0.99, 2x256 ReLU MLPs | IQL paper MuJoCo setting [1] |
| Eval | 10 episodes every 5k steps, deterministic mean action, fixed eval seeds | Matches IQL/CORL protocol [1, 8] |
| Final score | Mean of the last 5 evaluations (last 25k steps) | Less noisy than the single last eval; decide now, not after seeing results |
| Statistics | Mean, std, and stratified bootstrap 95% CIs + IQM via `rliable` | With 3 seeds, point estimates mislead [14, 15] |

**Stretch technique (only if Phases 1 to 9 are done early):** return-based trajectory reweighting [19] at `p = 0.05`. That paper studies exactly our setting (mostly poor trajectories, a few good ones) and shows IQL can fail to exploit the good ones. A one-cell comparison would make a strong discussion point.

### Phase 2: Data acquisition, validation and EDA
**Goal:** verified-clean datasets and a written EDA report that informs every later design choice.

**Why:** in offline RL the dataset *is* the environment. If you do not know its return distribution, episode lengths and state coverage, you cannot interpret your results. The EDA also gives you the numbers for the score normalization and the H1 argument.

**Tasks: integrity checks (`offrl/data/validate.py`, also run as tests)**
1. Counts match the Minari pages: 999,164 / 1,086 and 999,206 / 1,952.
2. Per episode: `len(obs) == len(actions) + 1`; rewards, terminations, truncations have length N.
3. No NaN or inf anywhere.
4. Actions within [-1, 1]; report the fraction at the bounds (saturation).
5. Each episode ends with exactly one of: termination, or truncation at step 1,000. Nothing terminates mid-episode.
6. Observation dims stay within [-100, 100] (Hopper's health bound).
7. No duplicated episodes (hash each episode's actions).
8. **Optional dynamics check:** for a sample of 1,000 transitions, reset the MuJoCo state from `obs` (x position is not in the obs but does not affect dynamics), apply the action, and compare with `next_obs`. Confirms the data matches the evaluation env.

**Tasks: EDA (`scripts/eda.py` + `offrl/analysis/eda.py`; full spec in `docs/specs/phase-2b-eda.md`)**
1. Episode length and return statistics and histograms, expert vs. simple.
2. Fall rate, and every statistic split by `fell` vs. `no_fall`. The returns are bimodal (simple: 66% of episodes fall), so a single mean hides the structure.
3. Per-dimension state statistics (descriptive only; training normalizers are fit per mixture, ADR-5) and velocity clipping per dimension.
4. Reward decomposition (survival + forward velocity - control cost), reconciled against the recorded rewards.
5. State coverage: PCA of states colored by source.
6. Source separability (kNN classifier AUC, split by episode) and action disagreement between kNN neighbours from each source. Tests the averaging story behind H1.
7. Random-policy return over 100 seeded episodes: the 0 of the normalized score (ADR-6).
8. Per-`p` reference curve (the score of each mixture's own episodes) and the IQL reward-scale preview per `p`.

**Deliverables:** `validate.py`, `tests/test_validate.py`, `report/data_audit.json`, `scripts/eda.py`, `report/eda_summary.json`, `report/eda_summary.md` (one page: numbers + 8 figures + "implications for modeling").

**DoD:** every integrity check and every EDA reconciliation check passes; `r_random` and `r_expert` recorded in `configs/base.yaml`; Phase 4 sanity bands recorded in `eda_summary.json`.

**Pitfalls:** computing statistics on `obs` including the final observation (biases means slightly; use `obs[:-1]` for state stats); eyeballing instead of asserting.

**References:** [5, 7, 3, 18] ([18] gives TQ and SACo, two dataset-quality measures you can quote for each mixture)

### Phase 3: Mixture builder and data pipeline
**Goal:** deterministic `p`-mixtures and a fast GPU replay buffer with correct normalization.

**Why:** the mixture is the independent variable of the whole project. If `p` is wrong or not reproducible, nothing after this means anything.

**Tasks**
1. `mixture.py`: shuffle episode IDs of each source with the mixture seed; take whole expert episodes until the expert transition budget `p * 900,000` is reached, same for simple with the rest; trim the last episode of each source to hit the budget exactly; write `.npz` + manifest (Section 3.4).
2. Flatten to transitions: `obs, act, rew, next_obs, done = terminations`. Keep `episode_id` and `source` columns for analysis.
3. Compute, per mixture: TQ/SACo-style summary (mean return, unique-state coverage proxy) and the actual `p`.
4. `normalize.py`: state mean/std from the mixture; reward scale from the mixture's episode returns; save both with the mixture so eval uses the same transform.
5. `buffer.py`: load everything onto the GPU once (900k x 30 floats is about 100 MB), sample with `torch.randint`.

**Deliverables:** five mixtures per seed in `/scratch/$USER/mixtures/`, `tests/test_mixture.py`, `tests/test_buffer.py`, `tests/test_normalize.py`.

**DoD (tests must assert):**
- exactly 900,000 transitions; `|p_actual - p| < 0.002`;
- same seed gives a byte-identical file (sha256), different seed differs;
- `p = 0` contains zero expert transitions and `p = 1` zero simple ones;
- no transition pairs an `obs` from one episode with a `next_obs` from another;
- `done` is 1 only on terminal steps, never on truncation;
- normalizer fit uses only the mixture's own data;
- per-`p` mixture scores and reward scales reproduce the Phase 2 previews (A11, A12 in `report/eda_summary.json`) for the same seeds.

**Decided in this phase:** ADR-9 (per-mixture reward scale, with the `p = 0` caveat). Full spec: `docs/specs/phase-3-mixtures.md`. Final mixtures use seeds 0 to 2; development mixtures (Phases 4 to 6) use seeds 100+, so no debugging decision is tuned on final data.

**Pitfalls:** trimming an episode and marking the cut as a terminal (it is not); fitting normalizers before mixing.

**References:** [1, 8, 16]

### Phase 4: BC and the evaluation harness
**Goal:** a working BC baseline and the evaluator every later run uses.

**Why:** BC is simple, so if it fails the bug is in the shared plumbing (data, normalization, eval), not in the algorithm. Debug the plumbing here, where it is cheap.

**Tasks**
1. `nets.py`: MLP, GaussianPolicy (state-independent log-std, mean through tanh), TwinQ, ValueNet.
2. `bc.py`: loss `-mean(log pi(a|s))`, implemented by calling the IQL policy loss with all weights = 1 (so the code path really is shared).
3. `evaluate.py`: recovered env via `dataset.recover_environment()`, normalized obs, mean action, 10 fixed seeds, returns raw return, fall rate and normalized score `100 * (R - R_random) / (R_expert - R_random)` (ADR-6). Built on `offrl.rollout.run_policy`. Seeds come from `offrl.rollout.eval_seeds` only: the datasets were collected from reset seeds 123 to 2074 (Phase 2, C9), and evaluating from those seeds would start episodes in training states (leakage; `tests/test_leakage.py` guards it).
4. `train.py`: loop with logging every 1k steps, eval every 5k, checkpoint every 25k, resume from latest checkpoint.
5. Sanity runs (local CPU or `gpu-short`, 100k steps is enough): BC at `p = 0` and `p = 1`, on **development** mixtures (seed 100+) with **development** evaluation seeds (`eval.seed_offset: 20000`); seeds 10000+ and mixture seeds 0 to 2 are reserved for the final grid.
6. Final score of every run: mean over the last 5 evaluations (pre-registered; no early stopping or checkpoint selection), with the final evaluation over 50 episodes because a fall is all or nothing. Report wording: disjoint seeds prevent exact replay of a training trajectory, but starting states stay close to training ones (reset noise 0.005).

**Deliverables:** BC learning curves at `p = 0` and `p = 1`, `tests/test_losses.py` (BC part).

**DoD:** BC at `p = 1` lands in `[80.3, 113.5]` and at `p = 0` in `[22.5, 85.4]` (lower bound: Phase 2 `sanity_bands`; upper bound: the dataset's best episode, decided 2026-11-16, D4), on development seeds 100 and 101, reported with fall rates; a miss is rerun at 300k and both are reported; no-fall return within 10% of the dataset's at both `p` (at least 10 no-fall episodes); `score(p = 1)` vs. `score(p = 0)` reported, not gated (spec Section 8.1); held-out expert action R^2 >= 0.8 on dataset episodes not in the mixture (D3); learned vs. residual action std and no-fall return vs. the dataset answer whether the data actions were noisy; killing and resuming a run is bitwise identical. Final score: mean of the last 5 evaluations, each over 50 episodes (D1). Spec: `docs/specs/phase-4-bc-eval.md`.

**Pitfalls:** evaluating with sampled actions instead of the mean; forgetting to normalize eval observations; eval env seeds not fixed (noisy curves that look like bugs).

**References:** [1, 4, 8, 11]

**Status (2026-11-17): DONE.** Official sanity job 11921436 (Tesla T4, commit `6d1c2b6`): all 15 checks pass; BC scores 82.1/81.9 at `p = 0` and 104.4/105.5 at `p = 1`; bitwise resume on real data. Results: `report/phase4/bc_sanity.json`, `report/figures/bc_sanity_curves.png`; compute: `report/compute.md`.

### Phase 5: IQL implementation and validation
**Goal:** a correct IQL that matches published behavior before it touches the grid.

**Why:** IQL has several small details (Section 5) that each cost 10 to 50 points if wrong. Validation on the easiest setting (`p = 1`) and a comparison against a reference implementation catches them.

**Tasks**
1. `iql.py`, update order per step: V (expectile loss vs. `min(Q1_target, Q2_target)`), then Q (MSE to `r + gamma * (1 - done) * V(s')`), then policy (clipped advantage-weighted log-likelihood), then soft target update. **As built (Phase 5 spec Section 2):** CORL's order: `V(s')` read before the V step, then V, Q, the soft target update, the policy (with the advantage from the pre-update V) and the actor schedule. Doing the soft update before the policy step is equivalent, since the policy step does not read the target. Official IQL feeds the updated V instead; CORL is the reference.
2. Unit tests for the math:
   - expectile loss with `tau = 0.7`: `u = 1` gives 0.7, `u = -1` gives 0.3;
   - with `beta = 0`, IQL policy loss equals BC loss on the same batch;
   - advantage weights never exceed 100;
   - with `done = 1`, the Q target equals `r`.
3. Validation runs, 2 seeds, 300k steps: IQL at `p = 1` and `p = 0`. **As built (Phase 5 spec Section 8):** 14 runs on development seeds 100 and 101: IQL at `p` in {1, 0.2, 0}, CORL and BC at `p` in {1, 0.2}; then, after the V1 miss, ours and CORL at `p = 1` on seeds 102 to 104 under a follow-up rule fixed in advance.
4. Reference comparison: run CORL's `iql.py` with a small Minari loader on the `p = 1` mixture (same seed and steps) and overlay learning curves. **As built (Phase 5 spec Section 5):** selected lines of CORL's `iql.py` are vendored unmodified in `src/offrl/_vendor/` and wrapped by `algos/corl.py`, so CORL runs through the same `train.py`, data, pre-flight and evaluator as ours instead of a separate loader; a test checks the vendored file's hash, and another matches our update to CORL's in float64.
5. Log diagnostics: mean V, mean Q, mean advantage, fraction of clipped weights. Q values should be stable, not growing without bound.

**Deliverables:** `iql.py`, extended `test_losses.py`, validation plot (ours vs. CORL). **As built:** the IQL tests are in `tests/test_iql.py` and `tests/test_corl.py` (I1 to I12), the losses in `algos/losses.py`; `report/phase5/` and `report/figures/iql_validation_curves.png`.

**DoD:** ~~IQL at `p = 1` normalized score >= 90; curves within the seed spread of CORL's; Q and V do not diverge.~~ (replaced 2026-11-20) As set in the Phase 5 spec (`docs/specs/phase-5-iql.md` Sections 8 and 10; user decisions D3 and D6): V1, IQL at `p = 1` within 10 points below BC at `p = 1` (two-seed means), evaluated and recorded (pass or fail), with the spec's seed 102 to 104 follow-up rule carried out; 90 at `p = 1` reported, not gated; V0 (one commit, clean tree, mixture hashes, reward scales and `done` counts checked), V2 (two-seed means of ours and CORL within 10 points at `p = 0.2`), V3 (after 50k steps Q and V finite and inside `[min(r_min, 0), max(r_max, 0)] / (1 - gamma)`, `V(s_0)` within 0.8 to 1.5 times the discounted return at `p = 1`, `q_mean` drifting at most 10% from 200k to 300k) and V4 (at `p = 1`, no-fall return within 10% of the expert's 4157 on at least 10 no-fall episodes) pass. **Result (2026-11-21):** V0, V2, V3 and V4 pass; V1 fails and is recorded (IQL 85.3 vs. BC 105.1); the follow-up rule says proceed (`report/phase5/`, README).

**Pitfalls:** using the online Q (not target) in the V loss; bootstrapping on truncations; forgetting the reward scaling, so `beta = 3` means something very different.

**References:** [1, 2, 4, 8, 10]

### Phase 6: Compute benchmark and Slurm pipeline
**Goal:** know exactly what the grid costs and launch it with one command.

**Why:** guessing compute leads to either over-requesting (long queues) or timeouts. Ten minutes of measurement saves hours.

**Tasks**
1. Time 10k steps of IQL with 1, 2 and 4 runs per GPU on `gpu-short`, and on CPU in `short`. Record steps/s and eval time.
2. Pick the configuration with the best runs-per-hour; set `--runs-per-bundle` and `--time` with a 50% safety margin.
3. `sweep.py`: expands a grid file into a run list, maps an array index to a bundle, skips runs that already finished (so re-submitting is safe).
4. Dry run: submit the array with `--steps 2000` to check paths, logs and resume.
5. Write `report/compute.md`: GPU type, steps/s, GPU-hours per run and total.

**Deliverables:** `slurm/grid.sbatch`, `sweep.py`, `report/compute.md`.

**DoD:** dry-run array completes with every run folder containing config, metrics and a checkpoint; resubmitting skips finished runs.

**Pitfalls:** writing outputs to `/home` (quota); log files with the same name across array tasks (use `%A_%a`).
